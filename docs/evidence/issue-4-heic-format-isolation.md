# #4: v3 피드백 이후 HEIC 형식 분리

2026-10-23 사용자는 갤럭시 원본, Samsung aux 연결 제거 대조군, 추가로 Exif/XMP를 제거한 ISO 대조군 모두 Google 포토에서 HDR로 밝게 보인다고 확인했다. v3 JPEG의 하이라이트도 개선됐다. 생성 HEIC는 JPEG보다 약하고 이전과 같아 보인다고 했다. 따라서 사용 중인 감상 환경에서 **적어도 제공된 ISO 대조군의 HEIC HDR 표시는 가능**하며, 삼성 전용 연결이 필수라는 가설은 이 사례에서 배제된다. 모든 ISO HEIC의 지원을 뜻하지 않는다. #4는 계속 미통과다.

## 비교 순서

색감과 HDR 의도는 유지하며 다음 가설을 분리한다.

1. 단색 HEVC Gain Map 처리: 같은 Gain Map 값을 일반 YUV420으로 부호화하면 결과가 달라지는가?
2. 큰 직접 부호화 이미지 또는 코덱 형식 처리: 기본 이미지 형식도 바꾸면 달라지는가? 필요하면 크기/타일 구조를 후속 비교한다.
3. 색 프로필 처리: 기본 이미지에 동일한 sRGB 의미의 ICC를 추가하면 달라지는가?

v4는 새 RAW 현상 정책이 아니라 로컬 진단용 컨테이너 파생 파일이다. 원본 RAW/HIF, 갤럭시 원본과 v3 파일은 수정하지 않았다. 제품 인코더와 제품 검증기의 허용 형식은 아직 변경하지 않았다.

| 파일 | v3 대비 변경 | 그대로인 조건 |
|---|---|---|
| A-gain420.heic | Gain Map을 중립 RGB YUV420으로 저장, 해당 hvcC/pixi 갱신 | 기본 이미지 압축 바이트, tmap 메타데이터, Gain Map 디코딩 값 |
| B-base420.heic | 기본 이미지만 YUV420으로 저장 | Gain Map 압축 바이트, tmap 메타데이터 |
| C-both420.heic | 기본 이미지와 Gain Map 모두 YUV420 | tmap 메타데이터; A/B의 조합 효과 비교 |
| D-base-srgb-icc.heic | 기본 이미지에 sRGB ICC 추가 | 두 압축 이미지와 tmap 바이트, 기존 NCLX |

YUV420 후보는 pillow-heif/libheif로 부호화한다. 픽셀 검증은 별도의 FFmpeg native HEVC 디코더와 NumPy ISO 수식으로 수행한다. `quality=-1`을 사용했지만 기본 이미지의 색차 서브샘플링까지 RGB 무손실이라고 주장하지 않는다. 기본 이미지의 실제 픽셀 차이를 보고한다. Gain Map은 RGB 세 채널이 같은 중립 영상이며 디코딩 값의 차이도 검사한다.

FFmpeg가 새 HEVC를 `yuvj420p`(8bit, full range)로 보고해 기존 제품 검증기의 제한에 걸렸다. 제품 코드에서 검사를 우회하지 않고, 이 형식과 BT.709 full-range 변환을 명시적으로 확인하는 비제품 진단 경로로 디코딩했다. 기존 기본 이미지/단색 Gain Map은 제품의 독립 디코딩 함수를 그대로 사용했다. 파생 컨테이너를 다시 파싱해 item 바이트와 tmap 보존도 확인한다.

진단 하네스는 무시되는 로컬 `artifacts/issue-4/prepare-format-controls.py`, 결과는 `artifacts/issue-4/recheck-v4/`에 둔다. 실제 Fold7 결과를 받기 전에는 어떤 후보도 제품 수정 완료나 #4 합격으로 처리하지 않는다.
