# Fold7 · Google 포토 실제 확인 (#4)

현재 사용자 응답: Fold7, OS/앱은 “최신버전”, Google 포토 백업은 **원본 화질**. 정확한 Android/One UI/Google 포토 버전 번호는 미확인이다. 2026-10-22 사용자 확인에서 JPEG만 Ultra HDR로 인식되고 HEIC는 인식되지 않았다. JPEG/HEIC 색은 이상하고 카메라 HIF만 정상으로 보고됐다. **#4 수용 실패이며 후속 배치/GUI 게이트는 미통과**다. JPEG 인식 표시를 실제 HDR 화질 승인으로 간주하지 않는다.

후속 사용자 확인: DSC07809가 **어둡고 채도가 낮으며 Windows에서도 동일**하다. 제공된 로컬 HEIC/JPEG/HIF 세 파일은 기존 비교 묶음과 SHA-256이 각각 동일했다. 이 폴더가 Google 포토에서 다운로드한 파일인지는 확인되지 않았으므로 클라우드 왕복 무변경의 증거로 취급하지 않는다. 기존 독립 파일 검사와 실기기 호환성·색감 수용은 별개의 판정이다.

## 색감 문제 진단 (2026-10-22)

HIF와 후보를 같은 방향의 최대 1000px SDR RGB로 읽고, HIF 인코딩 휘도 0.15~0.85 영역의 평균 휘도와 유채색 영역의 평균 HSV 채도를 비교했다. 아래 비율은 HIF 대비 값이며, 물리적 휘도나 색 정확도 인증이 아니다. 임시 하한 0.9는 보고된 어두움/저채도를 재현하기 위한 신호일 뿐, 과노출·색상 이동·국소 품질이나 사용자 수용을 보장하지 않는다.

| DSC07809 경로/실험 | 밝기 비율 | 채도 비율 | 결과 |
|---|---:|---:|---|
| 기존 비교 JPEG | 0.5791 | 0.7098 | 두 번 같은 실패 재현 |
| 인코딩 전 SDR | 0.5810 | 0.7140 | 저장 전부터 같은 증상 |
| LibRaw 자동 밝기만 활성화 | 0.5810 | 0.7140 | 실질 개선 없음 |
| 중간톤 곡선만 적용 | 0.9069 | 0.6635 | 채도 부족 지속 |
| 같은 곡선 + 제한된 채도 보정 | 0.9010 | 1.0546 | 이 사진의 임시 하한만 통과 |

실제 `convert_raw`로 새 HEIC/JPEG를 생성한 회귀 테스트도 기존 JPEG와 같은 0.5791/0.7098로 실패했다. 따라서 주된 어두움/저채도는 코덱 저장이나 Google 포토 업로드 이전의 RAW 현상/SDR 표현 생성 단계에 있다.

고정 중간톤+채도 후보를 다른 대표 사진에 적용하면 DSC07773은 1.2250/0.8414, DSC07793은 1.1492/0.8596으로 밝기가 과해지고 채도 부족도 남았다. DSC07796은 0.9734/1.0464, DSC07805는 0.9682/1.1255였다. **고정 보정 후보는 채택하지 않았다. 제품 현상 코드는 아직 수정하지 않았으며 색감 문제가 해결되지 않았다.** 실험 파일은 무시되는 로컬 `artifacts/issue-4-debug/`에만 보관한다.

별도 관찰: pillow-heif 1.8.1에서 생성 HEIC의 실제 픽셀 디코딩이 decoder plugin 오류로 실패했다. 같은 파일의 기존 독립 FFmpeg HEVC 디코딩/재구성과는 다른 경로다. 카메라 HIF의 픽셀 디코딩은 성공했다. 이 실패와 Fold7의 HDR 미인식 간 인과관계는 아직 확인하지 않았다.

사용자는 **HEIC 목표 유지, 색감 수정과 HEIC 호환성 추가 조사**를 선택했다. 색감 진단 결과만으로 #4를 완료하거나 #5 이후 작업을 시작하지 않는다.

## 수정 후보 v2: 재확인 대기

현상 정책을 `preview-calibrated-highlight-v2`로 변경했다. ARW 내장 JPEG의 휘도 분포와 평균 채도에서 전역 톤 곡선/채도 계수를 구하며, 실제 출력 픽셀은 16bit RAW 현상에서 만든다. 별도 HIF는 변환 입력이 아니다. HDR은 8bit JPEG를 확장하지 않고 float 렌더링, 원래 RAW 휘도의 하이라이트 가중치, RAW의 SDR 백색 초과분에서 생성한다. 모든 RAW 하이라이트 디테일의 보존을 입증했다는 뜻은 아니다.

현재 PoC는 내장 JPEG가 없거나 톤 분포가 퇴화한 ARW를 실패 처리한다. 확인한 대표 5장의 내장 JPEG에는 ICC/EXIF ColorSpace 표시가 없으며, 이 샘플 집합에서는 sRGB 기준으로 평가했다. 다른 카메라/색공간/37개 전체에 대한 검증은 아직 아니다. HIF와의 정확한 색 일치, 국소 피부색·노이즈·밴딩은 평균 수치만으로 판단하지 않는다.

HEIC 디코딩 문제는 단일 HEVC NAL 크기와 연결됐다. 기존 DSC07809/DSC07796은 각각 19,356,722/22,461,454 bytes의 단일 NAL로 pillow-heif에서 실패했고, 다른 세 대표는 16MiB 미만으로 성공했다. 사용 중 libde265 소스의 기본 NAL 제한도 16MiB다. DSC07809에서 x265 슬라이스 수만 4로 바꾸면 각 NAL이 4,500,866~5,374,461 bytes로 나뉘고 같은 디코더가 원래 4672×7008 픽셀을 정상 디코딩했다. 독립 FFmpeg HDR 재구성도 통과했다. 재현 가능한 빌드 패치를 추가했으며, 임의 사진 전체에서 NAL 크기를 보장하거나 **이 수정이 Fold7 HDR 인식까지 해결했다고 주장하지 않는다**.

새 DSC07809 HEIC의 HIF 대비 밝기/채도 비율은 1.0119/0.9505다. 이전 실출력의 0.5791/0.7098과 구분한다. 회귀 기준은 두 비율 모두 0.9~1.1이며, 원래 파일로 실패하고 새 실제 변환 파일로 통과했다. 이 기준은 보고된 어두움/저채도와 과도한 보정을 잡기 위한 제한된 지표다.

Android 16의 [공식 발표](https://android-developers.googleblog.com/2025/02/second-beta-android16.html)는 Ultra HDR HEIC 인코딩 지원을 설명하고, [AOSP DataSpace 정의](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/hardware/DataSpace.java)는 ISO Gain Map HEIF를 별도 데이터 공간으로 정의한다. 이는 사용자의 Google 포토 버전에서 이 파일이 HDR 표시된다는 보장은 아니다. 실제 앱/기기 결과를 계속 별도로 확인한다.

검증: Windows 실제 샘플을 지정한 전체 pytest는 **14 passed, 0 skipped (384.58초)**, `mypy src`는 5개 파일 통과했다. 명세/코딩 기준의 분리 검토에서 구현 결함은 각각 0건이었다. 실기기·사용자 화질 수용은 여전히 미완료다. 네이티브 라이브러리는 수정 대상을 Release로 재빌드했고 패치 역적용 검사로 이미 적용된 상태를 확인했다. 전체 의존성을 삭제한 클린 빌드를 수행한 것은 아니다.

재현 환경 변수: `RAWHDR_SAMPLE`은 DSC07773.ARW, `RAWHDR_COLOR_SAMPLE`은 DSC07809.ARW, `RAWHDR_HEIC`는 새 DSC07809.heic의 로컬 경로로 지정한다. `.venv/Scripts/python.exe -m pytest -q`가 단일 변환·비교 JPEG·색감·일반 HEIC 디코딩·독립 HDR 검증 회귀를 실행한다. 개인 샘플 미설정 시 관련 테스트는 건너뛰므로 기본 실행 결과와 구분해야 한다.

대표 5장 모두 새 HEIC를 독립 FFmpeg 경로로 검증했고, pillow-heif 실제 SDR 디코딩과 HEIC/JPEG 색감 지표도 통과했다. 원본 ARW/HIF 무변경을 확인했다. 다음은 HEIC의 수치이며, 용량은 최적화 전이라 기존 결과보다 커졌다.

| 사진 | 밝기 비율 | 채도 비율 | HEIC bytes | JPEG bytes | 재구성 HDR 최대 |
|---|---:|---:|---:|---:|---:|
| DSC07773 | 1.0028 | 0.9637 | 25,429,710 | 10,902,957 | 3.8867 |
| DSC07793 | 1.0034 | 0.9970 | 23,135,037 | 8,239,230 | 1.0000 |
| DSC07796 | 0.9789 | 0.9140 | 30,282,874 | 13,798,661 | 1.0153 |
| DSC07805 | 1.0038 | 0.9864 | 20,595,500 | 8,102,865 | 2.7890 |
| DSC07809 | 1.0119 | 0.9505 | 28,728,253 | 14,383,655 | 4.0178 |

재확인 묶음: 로컬 `artifacts/issue-4/fold7-check-v2.zip` (214,781,191 bytes), SHA-256 `635e8fd8cff1cf91bda6546b259816ba92c26a363330a73899157e639cfc913d`. README와 대표별 3종 파일, 총 16개 항목의 ZIP CRC 검사를 통과했다. 새 생성 파일에는 `-v2` 접미사를 붙였다. 이전 파일은 보존했다. 실제 Fold7 재평가를 요청했으며 **#4는 열린 상태로 유지**한다.

1. 로컬 `artifacts/issue-3/representatives/index.html`에서 파일 대응과 SDR 비교를 먼저 확인한다. 원본 HIF는 SDR 기준 자료다. 세 번째 PNG는 -2EV 진단 그림이며 HDR 성공 증거가 아니다.
2. 사용자가 직접 대표별 `.heic`, `.jpg`, `.HIF`를 Fold7로 원본 전송한다. HEIC/JPEG가 메신저 등에 의해 재인코딩되지 않게 원본 파일을 사용한다. 로컬 감상 결과를 먼저 기록한다.
3. 사용자가 Google 포토에 직접 원본 화질로 백업하고 완료를 확인한다. 로컬 파일만 연 결과와 업로드된 사진을 연 결과를 구분한다.
4. Fold7 내부 화면에서 같은 밝기·색상 모드·주변 조명 조건으로 HEIC/JPEG/HIF를 비교한다. OS/One UI, Google 포토의 정확한 버전, 밝기/자동 밝기/절전/색상 관련 설정을 기록한다.
5. 하늘·밝은 나뭇잎에서 실제 HDR 하이라이트 확장이 보이는지, 그늘이 불필요하게 들뜨지 않는지 확인한다. 인물의 피부색과 화이트밸런스, 하늘 계조의 밴딩, 노이즈, 방향을 확인한다. 단순히 전체 화면이 밝아지는 것과 하이라이트 표현을 구분한다.
6. 커버 화면에서도 같은 파일을 확인하고 차이/제약을 별도로 기록한다. SDR 환경에서는 기본 이미지가 정상인지 확인한다. 스크린샷만으로 실제 HDR를 통과 처리하지 않는다.
7. 업로드된 HEIC를 Google 포토에서 다운로드해 별도 폴더에 둔다. 이 파일은 에이전트가 다시 독립 검사하고 업로드 전과 해시/크기를 비교해야 한다. 원본 결과를 덮어쓰지 않는다.

- 내부 화면 피부색·WB·밴딩·노이즈·자연스러움: 통과 / 문제 내용
- 커버 화면 결과와 SDR 결과:
- 다운로드한 HEIC의 로컬 경로:
- 야경 추가 자료 여부: 현재 제공 샘플에는 없음

HEIC 성공과 사용자의 화질 승인이 없으면 #4를 닫지 않는다. JPEG만 성공한 경우도 HEIC 목표 미달이다. #4 통과 전 #5 전체 배치와 GUI 구현은 보류한다. 해당 제한은 GitHub #4 수용 기준과 ADR 0002의 선행 게이트다.
